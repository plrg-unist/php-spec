# Statics inside named functions

A static declaration inside a named user function binds its local variable to one persistent reference cell. The cell belongs to the source declaration and function identity. Later calls reuse it; unsetting or rebinding the local name does not erase or redirect the persistent entry. Different declarations retain distinct cells, while ordinary local and returned aliases may share a cell.

The compiler checks `$this` and duplicate names before the offending initializer, including dead branches. Because duplicate static names within one function are rejected, each admitted declaration origin identifies one persistent slot; nested named functions have separate origins. `CODESTATIC` records the source occurrence, local CV name, initialization and binding lines, and stored versus evaluated mode. Constant preparation happens before ordinary initializer compilation: a folded branch may remove an invalid unselected operand, while `@` remains an evaluated initializer even if its eventual operand is constant. Stored expressions use the existing constant pool at initializer FIELD1 without inventing an expression opcode; a bare declaration uses null. Direct superglobal access remains separate from a hidden local static CV named `$_GET` or `$GLOBALS`.

`STATICS` contains only initialized entries. Absence represents an initializer that has not completed; a reference cell containing null is initialized. The list owns each cell independently of call frames. Existing environment, returned-reference, array and pool owners participate in the same heap accounting and copy-on-write rules. Static cells survive function return and abrupt frame cleanup.

An evaluated initializer runs in the current local environment before the new binding replaces an earlier local or parameter reference. `STATIC_BIND` checks the persistent entry again after evaluation. A recursive call may have initialized it first: that cell wins, and the later outer operand is released without an unnecessary deferred read. Failure before binding leaves the current entry absent while earlier successful declarations remain initialized. Catch/retry observations are retained as explicit dependencies until exception execution is supported.

Resume validation checks source-authenticated declaration names, mode and lines, current task ownership, distinct persistent declaration/cell identities and live defined reference cells. It permits arbitrary consistent cell values and local aliases. At the active binding prefix, a direct CV retains its source variable identity and other operands retain owning value/reference shape. Suspended frames do not borrow the active result for validation. No initialization history or artificial recursion lock is introduced.

Main-unit, closure/arrow, method/trait and inherited statics remain later scope. Object destruction, exceptions, dynamic-source lifetime and remaining full-core obligations stay required. This increment does not close the function or storage family.
